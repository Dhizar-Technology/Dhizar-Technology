# Vector 1 (V1) — Risk Register

A living document. Review and update at the start of each phase. Purpose: name the ways this project could waste time/money/energy *before* they happen, per the explicit priority of not letting the team drift into unproductive work.

| # | Risk | Phase most relevant | Mitigation |
|---|---|---|---|
| 1 | **Signal quality too weak/noisy on a single dry electrode to reliably classify targets** | Phase 0 | This is exactly why Phase 0 is a dedicated, small, cheap feasibility spike before any game-building begins. If single-channel accuracy is poor, first try electrode type (wet gel), placement precision, and stimulus design improvements before concluding more channels are required. |
| 2 | **Team over-commits to a channel-count or hardware spec before evidence justifies it** | Phase 0–1 | The single-channel-first decision (Technical Primer §3, Milestones Phase 1 decision point) is explicit: expand channels only after measured evidence, not by default assumption. |
| 3 | **Scope creep into motor imagery / emotion detection / other BCI paradigms** | All phases | Technical Primer §2 table exists specifically to catch this. Any proposal to add a different signal paradigm gets checked against it in planning meetings. |
| 4 | **Photosensitive epilepsy / user safety incident during a demo or in the browser-based visualization tool** | Phase 1 onward, especially Phase 2 (investor demo), and any time the visualization tool is shown to someone outside the immediate dev team | Mandatory safety disclosure screen and stimulus-design constraints from Technical Primer §6, built in from Phase 1, not retrofitted — and enforced in the software tool as well as the hardware demo. Never demo to an external audience without it. |
| 5 | **Software team validates the pipeline against the wrong kind of data (e.g., non-human, non-SSVEP, or non-scalp datasets) and gets false confidence** | Phase 0–1 (software track) | Explicit guidance in `02-PROTOTYPE-BUILD-GUIDE.md §4`: only real human scalp SSVEP-EEG datasets (Tsinghua Benchmark, BETA, Zhu et al., etc.) are used to validate the classifier. The Allen Institute mouse dataset and similar resources are flagged as unrelated and excluded from validation use. |
| 6 | **Game partner builds content that isn't frequency/refresh-rate compatible, breaking classification** | Phase 1 | Share Technical Primer + Build Guide with the partner *before* they start building; agree on stimulus frequency set and refresh-rate constraints at kickoff, not discovered late. |
| 7 | **Custom "neural network" work started too early, before the CCA/FBCCA baseline works** | Phase 0–1 | Explicit sequencing in the Milestones document: FBCCA baseline first, deep learning is a Phase 3+ differentiator, not a Phase 0 requirement — though early experimentation by the ML engineer against public data can start in parallel once hired. |
| 8 | **Demo fails live in front of investors (cables, calibration, environment)** | Phase 2 | Dry runs in the actual room, backup recorded video, spare hardware — see R&D Roadmap demo-day checklist. |
| 9 | **Data privacy/consent gaps as team starts collecting tester EEG data** | Phase 1 onward | Draft a simple consent + data-handling policy before the first outside tester session, not after; revisit with a lawyer before Phase 3 scaled data collection. |
| 10 | **IP exposure from showing early tech to partners/investors without any protection** | Phase 2 onward | Early (even informal) conversation with a patent attorney before broad demoing; use NDAs for detailed technical discussions with new external parties. |
| 11 | **Overpromising accuracy/latency numbers to investors that later don't replicate outside the demo environment** | Phase 2 | Only present numbers actually measured across multiple people/sessions (per Milestones Phase 2 definition of done); be explicit in the pitch about what's proven vs. roadmap. |
| 12 | **Software track (website, visualization tool, ML experiments) drifts into a generic SDK/platform product instead of serving the gaming-controller product** | All software phases | `07-SOFTWARE-DEVELOPMENT-GUIDE.md` scopes each tool's purpose explicitly; review against that scope before adding features. |
| 13 | **Key-person / hiring risk: software or ML roles remain unfilled for an extended period, stalling the parallel software track** | Phase 0–1 | Keep the software-track backlog prioritized so a single early hire can make immediate progress (dataset-based classifier work needs no onboarding period waiting on hardware); consider a contractor/freelancer for the website specifically if a full-time hire is slow to land. |
| 14 | **Wireless final-product headset introduces latency/reliability regressions vs. the wired prototype** | Phase 4 | Treat wireless transition as its own dedicated engineering milestone with a defined latency budget, not an assumed drop-in replacement. |
| 15 | **Manufacturing/unit economics don't work at consumer price points** | Phase 4 | Run a manufacturing feasibility/cost study explicitly before committing to final industrial design, not after. |
| 16 | **Regulatory/compliance delays (wireless certification, consumer electronics safety) block launch timeline** | Phase 4–5 | Scope regulatory requirements early (Phase 4), treat as a parallel workstream, not a Phase 5 afterthought. |

**How to use this document:** at the start of each phase kickoff meeting, review the risks tagged to that phase and confirm mitigations are actually being acted on, not just written down.
